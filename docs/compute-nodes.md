# 컴퓨팅 노드 관리

기존 Ceph 기반 `ablestack-hci` 클러스터에 SCVM 없이 VM을 실행하는 호스트를 추가한다.
클러스터 종류는 유지하고 해당 호스트에만 `role: "compute"`를 기록한다.
`role`이 없는 기존 호스트는 HCI 호스트로 취급한다. PowerFlex, GFS 및
`ablestack-hci-filesystem`은 이 기능의 지원 대상이 아니다.

## 배포 및 준비

- 기존 물리 호스트 전체와 추가할 호스트에 이 변경을 포함한 Cockpit 플러그인을 배포한다.
  선택한 파일은 기준 호스트 접속에 사용하며 실제 추가는 기준 호스트의 현재 구성으로 처리한다.
  파일 전체 값의 차이로 추가를 차단하지 않고 참여 노드에 현재 구성을 동기화한다.
- 새 호스트에 호스트명, 관리 IP, HPN IP를 먼저 설정한다. 이 기능은 NIC, 브리지,
  라우팅 또는 IP를 생성하지 않는다. 기존 SCVM의 스토리지망까지 연결되어 있어야 한다.
- 기존 클러스터 SSH 키로 기존 참여 호스트, SCVM, CCVM에 root SSH 접속이
  가능해야 한다. 새 호스트의 키는 클러스터 구성 준비의 SSH Key 파일 단계에서
  선택하고 사전 확인 전에 적용한다. SSH 포트는 기존 `/root/.ssh/config`를 따른다.
- 새 호스트에 libvirt, Ceph/RBD 클라이언트, chrony 및 기존 nwfilter 파일을 준비한다.
  VM 정의나 기존 PCS 설정이 있는 호스트는 추가할 수 없다.
- 작업 기준 호스트는 `cluster.json`의 첫 번째 HCI 호스트이다. 등록된 HCI·컴퓨팅 호스트의
  Cockpit에서 실행해도 해당 호스트로 전달하며, 기준 호스트가 온라인이어야 한다.
  기준 호스트의 `/etc/ceph/ceph.conf`, admin keyring, Ceph libvirt secret과
  `/root/.ssh/id_rsa` 키 쌍이 필요하다. `rbd` 풀 접근도 검사한다.

## 추가

새 호스트에서 **클러스터 구성 준비**를 실행하고 HCI를 선택한 뒤 **클러스터 구성 파일**로 이동한다.
로컬 구성이 없는 상태에서도 화면에서 HCI를 선택하면 컴퓨팅 노드 추가를 선택할 수 있다.
SSH Key 단계에서는 기존 클러스터 키를 선택하고, 컴퓨팅 노드 추가 영역에서 기존
HCI 클러스터의 `cluster.json`을 선택한다. 가져온 파일은 추가 완료 전 로컬 구성 파일에
덮어쓰지 않는다. 기존 HCI 호스트에서 실행할 경우 현재 구성을 그대로 사용한다.
선택한 기존 개인키·공개키는 마지막 완료 실행 단계에서 적용한 후 접속 검사를 진행한다.
SSH 키 적용이 실패하면 추가 작업을 진행하지 않는다. 이미 키가 적용된 호스트는
기존 SSH 설정을 사용한다. 가져온 개인키는 기준 호스트에 접속할 때 임시 파일로
사용한 뒤 삭제한다. SSH 서비스와 포트에 대한 네트워크 접속은 가능해야 한다.
같은 줄의 **신규 클러스터 호스트 / HCI 노드 추가 / 컴퓨팅 노드 추가** 중 컴퓨팅 노드를
선택한다. HCI 노드 추가와 같은 **기존 파일 사용 → cluster.json 선택** 흐름을 사용한다.
파일을 읽으면 기존 HCI 구성 표와 CCVM·관리 NIC·PCS·시간서버 정보가 채워진다.
기존 노드는 읽기 전용이고 마지막에 컴퓨팅 노드 입력 행 하나가 추가된다.
새 행의 호스트명과 호스트 IP는 현재 호스트에서 자동 조회한다. IP는 기본 경로의
출발 주소를 사용하며, HPN IP는 직접 입력한다. 기존 HCI·VM 노드 추가의 새 행에도
같은 자동 조회를 사용하고 기존 행이나 사용자가 입력한 값은 덮어쓰지 않는다.
그 행의 **호스트명 / 호스트 IP / 호스트 PN IP(HPN IP)** 세 칸만 입력하며 SCVM 칸은
`-`로 표시한다. 기존 컴퓨팅 노드의 SCVM 칸도 `-`로 표시한다.
컴퓨팅 노드 추가 선택은 화면에서 HCI를 선택하면 활성화되고 VM·Standalone에서는 숨긴다.
클러스터 종류 단계의 다음 버튼은 네 가지 종류 중 하나를 선택해야 활성화된다.
선택을 해제하면 다시 비활성화된다.
추가 UI와 실행 분기는 `cluster-config-prepare.js`와 `cluster-config-prepare.html`에서 관리한다.
별도 추가 화면이나 기존 페이지를 숨기는 CSS를 사용하지 않는다.
**다음**에서는 필수 입력을 확인하고 기존 시간서버·설정 확인 화면으로 이동한다.
페이지 이동 중 SSH 키 적용이나 원격 접속 검사를 실행하지 않는다.
**완료**에서 SSH 키 적용·진행 중인 작업 확인·백엔드 사전 검사 후 추가한다.
설정 확인의 클러스터 구성 파일 영역은 기본적으로 접혀 있으며, 사용자가 펼치면 호스트 수 변경과
`role: "compute"` 노드가 추가된 전체 `cluster.json`, 적용 예정 hosts 항목을 표시한다.
컴퓨팅 노드에는 SCVM 별칭을 만들지 않는다. 실행 실패 시 기존 배포 진행 화면을
유지하고 실패 단계와 이후 단계를 `중단됨`으로 표시한다. 상세 오류는
`console.log`와 기존 `alert()` 확인창으로 출력하며 마법사 본문에는 실행 오류 문구를 표시하지 않는다.
추가된 실행 진행 문구는 콘솔로만 출력하고 기존 3단계 상태 표시는 유지한다.
SSH 오류가 문자열이나 problem 형식이어도 문구를 표시한다.
상단 상태 영역에는 컴퓨팅 노드 추가 버튼을 제공하지 않는다. 추가는 새 호스트의
클러스터 구성 준비 마법사에서 실행한다.
설정 제거 화면은 별도로 유지한다.

1. 이름/IP 중복, 대상 실제 호스트명과 NIC 주소, VM 부재, 기존 구성 및 SSH 접속을 검사한다.
2. 새 호스트에 기존 SSH 키 쌍, SSH 설정, chrony 설정, `/etc/ceph/`의 일반 파일,
   Ceph libvirt secret 및 존재하는 TPM/UEFI agent 설정을 적용한다.
   Ceph 파일은 keyring을 포함해 기준 호스트의 파일 권한을 그대로 유지한다.
3. Open vSwitch가 아닌 경우 기존 준비 절차와 같이 XML의 실제 필터 이름
   (`allow-all-traffic`, `allow-traffic` 또는 `allow-all`)으로 nwfilter와
   bridge netfilter 설정을 적용한다. OVS 환경은 기존 정책을 유지한다.
   해당 필터가 이미 등록되어 있으면 재정의를 건너뛰고 기존 필터를 사용한다.
   같은 가입 작업에서 필터 XML을 기록했다면 재실행 때 중복 조회하지 않는다.
4. SCVM HPN ping, SSH, `ceph -s`, `rbd ls`를 확인한 뒤 구성 정보를 배포한다.
5. 모든 물리 호스트와 기존 SCVM의 플러그인 구성 경로, CCVM의 `/etc/cluster.json`에 구성 파일을 동기화하고,
   각자의 로컬 별칭을 유지하며 `/etc/hosts`에 컴퓨팅 노드를 반영한다.

`ablestack.json`의 `bootstrap.ccvm`, `bootstrap.scvm`, `monitoring.wall`은 문자열 `"true"`로 설정한다.
SCVM 값은 UI 완료 상태이며 실제 SCVM을 생성하지 않는다. 보안 패치·라이선스 등 호스트별 실제 상태는 유지한다.
SCVM 생성, PCS 멤버 등록, OSD 추가 및 Mold 호스트 등록은 수행하지 않는다.
준비 완료 후 Mold에서 호스트를 등록한다. Wall 수집 대상 변경이 필요하면 기존
모니터링 구성 화면에서 설정한다. 해당 화면은 물리 호스트 수와 SCVM 수를 구분한다.

## 설정 제거

등록된 HCI·컴퓨팅 호스트 어디에서나 **스토리지센터 클러스터 상태 카드 → ⋮ 메뉴 → 컴퓨팅 노드 설정 제거** 화면을 사용한다.
제거 대상 컴퓨팅 호스트 자신에서도 실행할 수 있다. 컴퓨팅 호스트에서는
스토리지센터 클러스터 상태·인프라 클러스터 상태·클라우드센터VM 상태 카드만 표시한다.
클러스터 상태는 기존 HCI 호스트에서 조회하고 스토리지센터VM 배포 카드는 숨긴다.
스토리지 카드의 메뉴에는 컴퓨팅 노드 제거를 제공한다.
상단에는 컴퓨팅 노드 문구와 클라우드센터·모니터링센터 연결 버튼을 표시하며,
스토리지센터 구성 완료 시 해당 대시보드 연결 버튼도 표시한다.
목록·사전 확인·제거·재시도·오프라인 내부 정리는 모두 동일한 HCI 기준 호스트에서 처리한다.
실행 호스트에서 기준 호스트까지, 기준 호스트에서 참여 노드까지 기존 SSH 설정의 포트로
root 키 인증이 가능해야 한다. 기준 호스트 접속 실패 시 실행 호스트에서 대신 제거하지 않는다.
Mold에서 신규 배치를 중지하고 VM 이전·로컬 디스크 정리·호스트 등록 해제를 먼저 완료한다.
컴퓨팅 노드를 선택하면 호스트명·호스트 IP·HPN IP를 한 화면에 표시한다.
제거 전 확인에는 Mold 정리 완료 체크만 제공하며, 체크해야 사전 확인 버튼이 활성화된다.
대상을 변경하면 체크와 사전 확인 결과를 초기화한다. 호스트명을 다시 입력하지 않는다.
사전 확인 성공 후 설정 제거 실행 버튼이 활성화되며, 검사와 실행 중 스피너를 표시하고 입력을 잠근다.
이 화면의 신규 제거는 대상 노드에 접속하여 내부 설정까지 정리하는 방식으로 실행한다.

- 중지된 VM을 포함해 libvirt VM 정의가 남으면 일반 제거를 차단한다.
- 대상 노드의 `cluster.json`을 빈 초기 구성으로 만들고 `/etc/hosts`는 기본 localhost
  항목으로 초기화한다. `ablestack.json`의 bootstrap 완료 상태와 Wall 구성 상태를 false로
  바꾸고 compute 표시를 제거한다. 실제 보안 패치·라이선스 상태는 유지한다.
- 대상 노드의 공유 `id_rsa` 키 쌍과 임시 키를 제거한다. 구성 준비 단계에서 먼저 적용된
  공개키도 authorized_keys에서 제거한다. 다른 관리자의 공개키는 유지한다.
  클러스터 호스트에 대한 known_hosts 항목도 정리한다.
- 가입 과정에서 복사한 Ceph 파일은 제거한다. 가입 전 같은 경로에 파일이 있었어도
  복사 대상 파일은 제거하며, 복사 기록이 없는 다른 파일은 유지한다.
  Ceph libvirt secret과 그 밖의 가입 시 변경한 설정 파일은 가입 전 상태로 복원한다.
- 추가 과정에서 적용한 `allow-all` nwfilter와 전용 bridge sysctl·모듈 자동 로드 파일을
  제거한다. 기록된 가입 전 bridge 값을 복원하고 가입 과정에서 로드한 모듈은 해제한다.
  다른 nwfilter와 OVS 환경에서 유지하던 기존 정책은 변경하지 않는다.
- 생존 노드에서 해당 노드의 구성, hosts 별칭, known_hosts 항목을 정리한다.
  남은 호스트의 번호·공유 SSH 키·nwfilter 설정은 유지한다. VM 디스크와 NIC 설정도 삭제하지 않는다.
- 백엔드의 오프라인 제거는 전원 차단 또는 격리 확인 후 등록 정보만 제거한다.
  현재 제거 화면에서는 새 오프라인 제거를 선택하지 않으며, 기존 미완료 내부 정리 기록은 유지한다.
  대상 호스트에 남은 키와 설정은 삭제되지 않는다. 화면에 **내부 정리 미완료**를 남기며,
  관리 접속 복구 후 **대상 호스트 내부 정리**를 실행해야 재등록할 수 있다.
  공유 키 자체를 폐기하는 작업은 아니므로 격리는 내부 정리까지 유지해야 한다.

## 실패 및 재시도

작업 기록과 가입 전 파일 백업은 root 전용 `/var/lib/ablestack/compute-nodes/`에 보관한다.
백업에는 인증 정보가 포함되므로 권한을 변경하거나 로그에 공개하지 않는다.
동일 기준 호스트에서 작업을 직렬화하며, 미완료 작업이 있으면 새 작업을 차단한다.
설정 제거 화면의 **처음부터 다시 실행**을 누르면 모든 참여 노드의 동기화를 처음부터 다시 실행한다.
대상 내부 정리가 아직 끝나지 않았다면 내부 정리부터 다시 실행한다. 이미 정리 완료한 대상은
SSH 키가 제거되므로 재접속하지 않고 완료된 내부 초기화를 유지한다.
컴퓨팅 노드 추가에는 별도 재시도 버튼을 제공하지 않는다. 같은 호스트명·호스트 IP·HPN IP로
설정 확인에서 **완료**를 다시 실행하면 SSH 키 적용, 신규 노드 준비와 전체 구성 동기화를 처음부터 다시 실행한다.
가입 전 백업과 동일 작업 ID는 유지하며 완료 단계 건너뛰기로 SSH 준비를 생략하지 않는다.
다른 노드·다른 IP 설정·제거 작업이 남아 있으면 자동으로 이어서 실행하지 않고 차단한다.
가입 후 변경된 `/etc/hosts`는 제거 시 localhost 기본 항목으로 초기화하고,
`/etc/chrony.conf`는 가입 전 백업으로 복원한 뒤 chronyd를 재시작한다. 이 두 파일의 일반 변경은 제거를 차단하지 않는다.
다른 파일이나 nwfilter의 변경 보호와 초기화 도중 파일 변경 검사는 유지한다. 심볼릭 링크도 거부한다.
대상 노드 초기화 중 실패하면 SSH 인증을 유지한 상태로 재시도하며, 키 정리는 나머지
설정 처리가 끝난 후 수행한다.
자기 자신을 제거해도 이미 연결된 SSH 세션으로 결과를 수신한다. 나머지 노드의 동기화는
기준 호스트의 키로 진행하므로 초기화된 실행 호스트의 키에 의존하지 않는다.
자기 자신 초기화 후에는 로컬 목록을 다시 조회하지 않으며, 완료 안내에 기준 호스트의
호스트명과 IP를 표시한다. 처음부터 다시 실행과 후속 관리는 그 호스트의 Cockpit에서
진행한다. 초기화된 호스트에 관리용 공유 개인키를 별도로 남기지 않는다.
기존 클러스터 구성 마법사와 동시에 멤버 구성을 변경하지 않는다.
원격 작업은 최초 실행한 Python 소스를 SSH의 표준 입력으로 전달하고 이후
기준 호스트에서 대상 노드로 전달할 때도 같은 소스를 사용한다.
`virsh` 실패 메시지에는 실패한 하위 명령 이름을 포함하며 인증 값은 출력하지 않는다.

사전 확인은 읽기 검사이며 네트워크·인증의 실제 적용 검사는 추가 실행 중 수행된다.
추가 중 오류가 발생하면 일부 설정이 이미 적용되어 있을 수 있다. 원인을 해결한 뒤
재시도한다. 작업 기록을 임의로 지우거나 다른 기준 호스트로 교체하지 않는다.

## 검증

실제 클러스터 배포 전에는 테스트 클러스터에서 SSH 포트, Ceph secret, HPN 연결,
Mold 등록 후 VM 생성·이전, 온라인/오프라인 제거를 확인해야 한다.


같은 호스트명의 컴퓨팅 노드를 다시 추가하면 기존 번호를 유지하고 해당 항목을 갱신한다. 중복 행은 생성하지 않으며 SSH 준비와 동기화를 다시 수행한다. 기존 HCI 호스트를 컴퓨팅 역할로 전환하는 작업은 이 기능에 포함하지 않는다.
